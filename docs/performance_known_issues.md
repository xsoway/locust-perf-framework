# 性能已知问题模式库（Performance Known Issues）

供报告分析 Agent 在 LLM 归因时检索对照，也供测试/开发人员快速定位。每条包含：

- **指标特征**（如何识别）
- **可能成因**
- **验证方法**（反证 / 进一步采集）
- **优化建议**（含优先级）

> 使用方式：当压测结果出现某种指标特征时，先在本库检索最相似的模式，再结合当前证据链下结论。不要跳过证据直接套结论。

---

## 1. 慢查询（数据库层）

- **特征**：RT 在高并发时飙升；数据库 CPU/IO 升高；slow-query 日志出现 `SELECT * ... WHERE` 全表扫描（扫描行数巨大）。
- **成因**：缺索引、SQL 写法差、未命中联合索引。
- **验证**：EXPLAIN 看 type/rows；对比慢 SQL 出现时间与 RT 飙升时间轴是否对齐。
- **建议**：
  - 【必须修】为高频 where 列加索引（预期查询耗时 -80%+）。
  - 【建议】改写 SQL、减少 `SELECT *`。

## 2. 连接池耗尽

- **特征**：错误类型出现"connect timeout"/"pool exhausted"；连接池利用率接近/达到 100%；并发高时排队数增长。
- **成因**：池 max 太小；或慢查询/慢下游把连接占满，新请求排队。
- **验证**：查看连接池活跃数 vs 峰值；关联是否同时有慢 SQL。
- **建议**：
  - 【必须修】调大池上限（要同时评估 DB 侧承受力）。
  - 【建议】修复占用连接的慢 SQL/慢下游。

## 3. Redis 缓存碎片化 / 热点穿透

- **特征**：缓存命中率在高并发时突然暴跌（如 92%→15%）；DB QPS 同步飙升。
- **成因**：缓存 key 设计含分页/高基数字段导致碎片化；或热点 key 集中访问；maxmemory 淘汰。
- **验证**：查看命中率曲线与 DB QPS 是否同拍；检查 key 分布。
- **建议**：
  - 【必须修】修正缓存 key 设计（去掉分页参数 / 用 list 按 offset 截取）/ 热点 key 加小随机错峰。
  - 【建议】给 DB 加本地/二级缓存。

## 4. GC 风暴（Java 服务）

- **特征**：RT 周期性抖动；Full GC 频繁且时长增加；应用 CPU 高但业务逻辑消耗小。
- **成因**：堆内存过小、对象创建频繁、短生命周期大对象。
- **验证**：看 GC 日志频率/停顿时间与 RT 抖动是否对应。
- **建议**：
  - 【必须修】优化对象分配（减少短命大对象）。
  - 【建议】调整堆大小 / 改用合适 GC 策略。

## 5. 线程池耗尽

- **特征**：TPS 触顶不再增长；出现"thread pool"相关拒绝/排队；线程利用率 100%。
- **成因**：线程数配置过小；或单请求处理慢（同步阻塞/外部依赖慢）导致线程被占满。
- **验证**：看线程池活跃=最大；关联外部依赖 RT。
- **建议**：
  - 【必须修】修慢的下游 / 阻塞点。
  - 【建议】适当调线程数或改异步处理。

## 6. 基础设施资源触顶（CPU/内存/IO）

- **特征**：服务器 CPU>90% / 内存持续上涨（疑似泄漏）/ 磁盘 IO 高 / 网络丢包。
- **成因**：服务本身瓶颈 / 代码低效 / 内存未释放 / 带宽不足。
- **验证**：监控资源曲线与压测阶梯是否逐级抬升；内存是否单调上升（泄漏）。
- **建议**：
  - 【必须修】定位高 CPU 函数 / 修复内存泄漏。
  - 【建议】扩容（机器规格 / 实例数），注意压测机自身是否先触顶（压测机会话失真）。

## 7. 压测机自身成为瓶颈（数据失真）

- **特征**：压测机 CPU/内存/网络先于被测服务触顶；后段数据虚高或失真。
- **成因**：并发线程数超过压测机承载；缺分布式。
- **验证**：监控压测机 CPU/内存/网络，红线：CPU>70%，内存>75%，网络>60%。
- **建议**：
  - 【必须修】降低本机并发或增加分布式 Slave 节点。
  - 【建议】按"单台 4C8G 约 600 并发"估算节点数。

---

## 附：验证时不要犯的错误

- 只看平均值不看分位数。
- 压测环境与生产配置不一致导致结论失真。
- 找到瓶颈后不做**相同压力回归验证**。
