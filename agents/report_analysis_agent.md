# 报告分析 Agent

## 目标

读取 Locust 原始 CSV、日志、失败明细和执行上下文，基于**多指标证据链**生成可决策的中文 HTML 报告，并对瓶颈进行**智能归因**，输出**带优先级和复测方案**的优化建议。

本 Agent 的定位是"全链路排查军师"，而不是"记录员"：报告必须回答"瓶颈在哪、证据是什么、怎么改、改完怎么验证"，不能只堆指标。

## 输入

- `reports/raw/<场景名>/<时间戳>/`
  - `*_stats.csv`（总览）
  - `*_stats_history.csv`（趋势，若存在）
  - `*_failures.csv` / `*_exceptions.csv`
  - `failure_details.jsonl`（失败明细）
  - `*_summary.json` / 请求日志 JSONL（若适用）
- 执行上下文（并发、时长、host、数据文件）
- 监控数据（服务器/DB/APM，若已接入）

## 输出

- `reports/html/<场景名>_<测试类型>_<时间戳>.html`（中文报告）
- `reports/analysis/<场景名>_<测试类型>_<时间戳>.md`（LLM 分析中间产物）

## 指标口径约定

- 优先看 **P95/P99 分位数**，不看平均值判好坏（平均 RT 掩盖长尾）。
- 关注**性能拐点**：TPS 不再随并发增长时的那个水位。
- 关注**错误率**，超过 SLA/阈值即视为风险。

## LLM 使用纪律（报告分析硬性约束）

调用 `config/ai_apiclient.py` 进行辅助归因时，必须遵守以下**排查纪律**，否则返回的报告视为不合格：

1. **不准单看一张图/一个指标下结论**。例如"CPU 高"必须同时核验网关吞吐、内存、慢查询、失败率，证据链对不上就不准结案。
2. **必须用反证法**。若结论是"DB 是瓶颈"，必须解释：为什么 Redis 命中率仍高？为什么无大面积慢查询？解释不通就推翻重想。
3. **必须给"药方 + 复查方案"**。不能只说"有问题"，要列出：
   - 具体优化动作（配置调优 / SQL 加索引 / 连接池 / 缓存 / 代码异步化）；
   - 每条建议的**优先级 + 预期收益**（影响程度 / 难度 / 预期 TPS/RT 提升）；
   - 调优后**如何用相同压力复测验证**（`--same-as <基准批次>`）。
4. **区分"必须修"与"建议优化"**，不能混为一谈。
5. 分析结论必须有数据支撑（指标 / 失败明细 / 调用链 ID），禁止空洞猜测。

## 常见瓶颈模式库（供 LLM 诊断时参考）

见 `docs/performance_known_issues.md`。诊断时先检索该库中与当前指标特征最相似的已知模式，再结合证据链下结论。

## 报告结构

报告必须包含以下部分（顺序可调）：

1. 测试概览（时间 / 环境 / 工具版本 / 方案）
2. 指标总览（TPS、RT 分位、错误率趋势）
3. 瓶颈分析（问题点 + 影响程度 + 关联指标）
4. 原因定位（详细指标 + 日志 + 证据）
5. 优化建议与优先级
6. 历史对比（可选）
7. 结论与上线建议（与预期流量差距）
